# Design Retrospective

Read this when a design project ships or completes — structured reflection on what worked, what did not, design-debt health, and how the person's design decisions are evolving, including the on-request longitudinal taste reflection.

Back-link: [Lane D — Design Record, Debt & Handoff](../lane-d-memory.md)

A retrospective is not a post-mortem. It examines the whole process — wins, misses, surprises, and taste evolution — and turns hindsight into foresight for the next project. Retrospective reflection turns project evidence into evidence-backed learning about how the person designs: it **describes** habits, it never sets rules for future work.

## When to use

- After the project is declared complete
- When the user says "let's reflect" or "what did we learn?"
- At natural project milestones (end of a major phase or sprint)
- When restarting work on a project after a break
- When the user asks for a longitudinal taste reflection — "what's my taste?", "how do I decide?", "what are my patterns?" Offer it once the record has **at least three projects** of history; below that, say the evidence is insufficient. Articulating one's own style for a portfolio or a team is also a valid request.

## Process

### Step 1: Gather evidence

1. Read the project design record — decisions, handoffs, open questions
2. Read the starting taste profile — what was known then vs now
3. Review user overrides — every correction, redirect, and override
4. Review critique and accessibility findings
5. Review fix rounds — how many, what was fixed, what kept coming back
6. Check the original brief — what was asked for vs what was delivered

### Step 2: Evaluate what worked

| Decision | Why it worked | Evidence |
|----------|---------------|----------|
| [decision] | [why it was the right call] | [user approved, critique passed, no fix rounds] |

Look for decisions that sailed through critique, choices the user explicitly praised, accessibility approaches that enhanced rather than constrained the design, and moments that reveal something characteristic about how the user designs (to note in the record — not to apply later).

### Step 3: Evaluate what did not work

| Decision | What went wrong | Root cause | Fix rounds |
|----------|-----------------|------------|------------|
| [original decision] | [what happened] | [misread brief? ignored taste? wrong assumption?] | [iterations to fix] |

Look for user overrides (what signal was missed), findings that returned in multiple fix rounds, accessibility issues that should have been caught in design rather than review, moments of premature convergence on one direction, and taste-profile mismatches (an old preference applied to a new context).

### Step 4: Evaluate the process

- **Efficiency:** fix rounds (necessary or preventable?), phases skipped, working mode used and whether it served the project
- **Handoff quality:** were handoffs specific enough; where was information lost between phases
- **Debate moments:** decisions that should have been debated but were not; debates that did not need to happen; whether debate outcomes held
- **User engagement:** how often the user overrode or redirected; whether overrides clustered in one area (a systematic gap)

### Step 5: Review design debt

- **Register status:** items created / resolved / accepted / still open / escalated
- **Debt patterns:** most affected persona, most common source, average age of open items
- **Debt health:** are we resolving debt faster than creating it; are the same issue types recurring; did any accepted debt matter more than expected

### Step 6: Taste evolution — project observations and the longitudinal synthesis

This section has two levels of analysis. Keep both; do not duplicate prompts between them.

**This project's observations** (descriptions for the record, never defaults):

- Recurring decisions reinforced — now seen in [N] projects, per [evidence]
- New habits or inclinations noticed — first seen here, per [evidence]
- Reversals — what the user moved away from, corrected, or changed their mind about, and why
- Surprises — chose [X] over [Y]; what was characteristic or unexpected

**Longitudinal taste reflection** *(from the former taste-report; personal layer only)*. When the record holds enough history (three or more projects) or the user asks, synthesise **across** projects — the patterns the designer might not see themselves:

- **In one line** — the sharpest characterisation of how they design
- **How they decide** — observations about decision-making, each tied to evidence (e.g. "you subtract before you add — overrides almost always remove an element rather than restyle it")
- **What they reach for** — recurring moves and defaults, framed as instincts, not rules
- **What they reject** — the anti-patterns, synthesised into a point of view
- **How taste is evolving** — what has hardened from soft to strong, what has changed direction, what is newly appearing, with movement over the project history
- **Possible blind spots** — surfaced gently, as questions, never verdicts
- **Where the signal is thin** — what the record does not yet know; confidence vs guess

Editorial rules for the synthesis:

1. **Synthesise, do not transcribe.** The value is patterns across entries, not re-listed table rows
2. **Every claim cites evidence** — projects, overrides, repeated decisions. No evidence, no claim
3. **Describe decision-making, not just preference.** "Decides colour last, after structure is settled" is insight; "prefers muted palettes" is a lookup
4. **Be honest about confidence and thin evidence**; do not manufacture a richer picture than the data supports
5. **Blind spots are questions, not judgements**
6. **Stay in the personal layer.** The synthesis describes portable, personal tendencies only. Client- or project-specific requirements (any project's design spec) are that client's, not the person's; if client-bound entries leaked into the personal record, flag them as contamination rather than reporting them as taste

### Step 7: Carry-forward items

- Broad lessons that apply to the next project
- Process improvements to try
- Taste insights to remember (as observations, not rules)
- Open questions for next time

### Step 8: Compile and present one deliverable

Compile everything into a single retrospective document — summary, what worked, what did not, process assessment, design debt, taste evolution (including the longitudinal reflection when warranted), and carry-forward — and present a concise summary to the user: top wins, top misses, taste learned, debt status, and carry-forward.

Producing the report does **not** itself edit the record: it reflects, it does not rewrite. Updating the personal design record is a separate, evidence-backed action (Step 9).

### Step 9: Update the design record

Add this project's evidence-backed observations to the personal design record: descriptions of how the user designs — habits, inclinations, reversals — with evidence. Never promote a one-project observation or a client-specific demand into portable taste or a future-project instruction.

## Integration

- **Reads:** project design record, taste profile, critique documents, verification results
- **Writes:** the single retrospective deliverable; evidence-backed observations added to the personal design record as a separate step
- **Boundaries:** the report reflects the record; it never rewrites it, and observations never become prescriptive input for future work

## Anti-patterns

| Pattern | Why it fails |
|---------|--------------|
| Skipping the retrospective because the project "went fine" | Even smooth projects teach; "why did this go well?" is as valuable as "why did it go wrong" |
| Blaming the workflow instead of missing context | If the output was wrong, the question is what context was missing, not who executed it |
| Only looking at failures | Wins are data too; understanding them is how they repeat |
| Not adding observations to the record | The record is only honest if kept current |
| Running the retrospective without user reflection | Reflection needs the user's own input; pause for it |
| Promoting one project's demands to portable taste | A client's requirement is not the designer's instinct |
| Transcribing the profile instead of synthesising | Reformatting tables is not reflection; the value is cross-project patterns |
| Reporting client-specific signals as personal taste | That is contamination, not taste |
